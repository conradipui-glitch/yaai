# P0-B.4 — практическая независимая слепая проверка

Этот workflow **не требует платных API** и не выполняет поиск
предприятий, отправку сообщений или изменение чужих сайтов.
Он отделяет **предварительные ответы автора набора** от
**самостоятельного решения внешнего рецензента**. Цель — не
превратить качество будущих рекомендаций в самооценку модели.

## Удобный режим: интерактивная страница вместо ручного JSON

Новая локальная форма: [tools/operator-review/index.html](../../../tools/operator-review/index.html).
Её можно открыть прямо из клона репозитория (обычный HTML-файл).
В ней 19 случаев, сведения об источниках и наблюдениях, выбор решения,
поля обоснования и контраргумента, кнопка сохранения каждого решения,
переходы между случаями и экспорт `review.json`. Форма адаптирована
под узкий экран, но **живой визуальный браузерный QA ещё требуется**
перед объявлением интерфейса полностью проверенным.

**Как пользоваться:** сначала выполните команду `prepare` ниже,
затем откройте HTML и загрузите **только blind.json**. Проверяйте случаи
без предварительных меток. После каждого сохраните решение, в конце
скачайте `P0-B.4-review.json`. Чтобы продолжить, загрузите обратно
`blind.json` и скачанный `review.json`. Не доверяйте странице
автоматическую проверку источников — публичные URL надо открыть лично.
Сохранение в браузерный localStorage, сеть и фоновое API отсутствуют;
при закрытии несохранённые в файл ответы теряются. Загруженные данные
живут только в памяти текущей страницы; **экспортируйте периодически**.

В завершение запускайте CLI `verify` и, только когда
все записи проверены независимо, `compare`. При недостатке
данных выбирайте честное `cannot_adjudicate`: оно **блокирует**
приёмку, пока обстоятельства не выяснены. Галочки о человеческой
независимой проверке — осознанное заявление, не формальность.

## 1. Создать чистый пакет и шаблон только для рецензента

Запуск из корня клона YAAI с Node.js 20+:

```bash
mkdir -p local-review
npm run playbook:operator:blind -- prepare \
  --blind local-review/P0-B.4-blind.json \
  --template local-review/P0-B.4-review.json
```

**Важно:** не отправлять рецензенту исходный
`p0-b4-reference-candidates.json`, в нём содержатся
`referenceDecision`. В `P0-B.4-blind.json` этих полей
нет. Шаблон пустой и не содержит ожидаемых решений.
Лучше хранить оба файла **вне публичного Git-репозитория**:
пути выше приведены для удобства; перед запуском выбрать
отдельный приватный каталог либо добавить его в локальный
`.git/info/exclude`. CLI не перезаписывает существующие файлы.

## 2. Независимый рецензент сначала читает только blind.json

Рецензент не должен быть автором предварительных меток. Для
каждого из 19 случаев он читает `sources` и `observations`,
при наличии публичного URL самостоятельно открывает его и
записывает, какую страницу видел, когда и какой вывод допустим.
Для синтетических примеров нельзя писать, что проверены
живые сайты: их ссылки `fixture.example` заведомо выдуманные.

Пример **структуры одной записи**, НЕ готовый ответ и НЕ
человеческая разметка (вставить правильные IDs из blind pack):

```json
{
  "caseId": "s01",
  "status": "hold_for_review",
  "evidenceIds": ["a"],
  "checkedSourceIds": ["site"],
  "sourceCheck": "synthetic_only",
  "reason": "Здесь собственный аргумент рецензента на 12+ символов",
  "alternativeExplanation": "Что может объяснить наблюдение иначе?",
  "nextCheck": "Какую проверку выполнить, чтобы решить спор?",
  "proposedAction": null,
  "reviewedAt": "2026-10-29T12:00:00Z"
}
```

Поля выше **иллюстрируют формат и не представляют правильную
метку для s01**. Возможные `status`:
`propose_draft`, `hold_for_review`,
`insufficient_evidence`, `cannot_adjudicate`.
Последнее состояние честно блокирует приёмку, пока нельзя
разобраться в причине.

`sourceCheck`:
- для синтетических случаев — только `synthetic_only`;
- для публичных — `checked_current_page` (проверен
  актуальный URL), `checked_saved_paraphrase` (оценён
  исходный текст, но не актуальный сайт) или `unavailable`.
  Не отмечать `checked_current_page` без реального
  просмотра URL; инструмент не способен подтвердить это сам.

Только после **собственного полного решения** рецензент
отмечает в `reviewer`:
- `alias` — псевдоним, без персональных данных;
- `isHuman: true` — только если действительно человек;
- `independentOfCandidateAuthor: true` — если он не создавал
  исходные `referenceDecision`;
- `blindedUntilSubmission: true` — если предварительные
  ответы не были просмотрены до фиксации решений.

Это **самостоятельная декларация**, а не криптографическое
доказательство того, кто сидел за компьютером. Ни сервис,
ни ИИ не должны проставлять эти флаги от имени человека.

## 3. Проверить полноту и связи

```bash
npm run playbook:operator:blind -- verify \
  --blind local-review/P0-B.4-blind.json \
  --review local-review/P0-B.4-review.json
```

`verify` проверяет version hash, все ID случаев/источников/
наблюдений, повторные строки, причину, контраргумент, дату,
пределы позитивных решений и наличие независимой декларации.
Неполный отзыв возвращает ненулевой код; он не является
«успешным результатом проверки».

## 4. После фиксации 19 решений сравнить с предварительными

```bash
npm run playbook:operator:blind -- compare \
  --blind local-review/P0-B.4-blind.json \
  --review local-review/P0-B.4-review.json
```

До закрытия всех случаев эта команда не выдаёт ответы автора
набора. После закрытия она показывает **согласия и расхождения**
с предварительными модельными метками — это **не accuracy/precision
работающего YAAI**, поскольку он ещё не исполнял Playbook в
исследовании. Сначала разбирать спорные места, затем сохранить
отдельный auditable adjudication artifact; исходный набор и
историю не перезаписывать.

Если контент публичной страницы изменился, фиксировать новую
дату/URL и причину. Само изменение источника не делает старую
датированную запись «ложной». Смотрите
[повторную проверку пяти ссылок](../../../docs/acceptance/P0-B.4-source-recheck.md).

## 5. Приёмка и границы

Текущий статус [P0-B.4](../../../docs/acceptance/P0-B.4.md) —
`AWAITING INDEPENDENT HUMAN REVIEW`. Новый workflow улучшает
практическую доступность проверки, но **сам по себе gate не
закрывает**.

После фактического независимого заключения — запись решения
ACCEPT/REWORK/BLOCK в Acceptance Card; **только после ACCEPT**
переход к P0-B.5. Настоящий сравнительный quality benchmark
с привлечением модели и измерением ложных предложений
является содержанием P0-B.5, не этого офлайн-инструмента.
