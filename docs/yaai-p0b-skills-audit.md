# P0-B — первый аудит Agent Skills для YAAI (2026-10-28)

**Статус:** первичный документальный аудит завершён; P0-B как
этап разработки **ещё не принят**: не проведены сравнительный бенчмарк
на размеченных реальных наблюдениях, проверка инфраструктурных
зависимостей и validation одного итогового playbook.
Никакие внешние скрипты/Skills не установлены и не выполнялись,
платных API-вызовов и контактов с кандидатами не было.

Рядом: [Product Blueprint v2](yaai-product-blueprint-v2.md),
[Operator Mode](yaai-operator-service-mode.md),
[Opportunity Radar](yaai-opportunity-radar.md).

## A. Зачем и как проверяем

Цель — не скопировать длинную библиотеку инструкций, а выбрать
**воспроизводимую методику, подходящую для одного пользователя
с локальным движком, российскими источниками и низкими затратами**.

Для оценки используются шесть критериев:
1. Чёткие входы, границы, шаги и выходы (repeatability).
2. Provenance: original source, observed/derived/unknown, дата,
   подтверждения/возражения и проверяемые связи.
3. Практическое решение предпринимателя, а не только объём отчёта.
4. Доступность для существующих YAAI Wordstat/SERP/MCP;
   платные или неподключённые зависимости явно отделены.
5. Safety: источник/лицензия, code review, законность/ToS, стоимость,
   разрешения и запрет автоматического outreach.
6. Возможность **проверить качество** на отложенной размеченной
   выборке, включая false positives и негативные примеры.

**Важное различие:** ревью SKILL.md — оценка обещанной методики;
не проверка, что она реально эффективнее наших Skills. GitHub stars
и маркетинговые отзывы не являются доказательством качества.
Числовые «порог 5 отзывов» или «Hot = 20% лидов» в чужом Skill
не превращаются без теста в фундаментальное правило YAAI.

## B. Что у нас уже есть

Все 11 собственных `.agents/skills/*/SKILL.md` прочитаны.
Имеющийся набор: yandex-keyword-research, competitor-evidence,
content-gap, distribution-intelligence, cheap-evaluation,
pain-discovery, page-plan, rank-tracker, seo-review, seo-report,
yaai-setup.

**Сильные стороны:** реальные метрики с границами интерпретации;
Wordstat/SEO с проверяемыми ссылками и сохранёнными файлами;
запрет суммирования пересекающегося спроса; раздельные
измерения vs гипотезы; бюджетный Jev как семантический фильтр;
существующие read-only MCP, task и Studio/Pain проекции.
Внешние Skills могут **расширить методологию**, но их нельзя
поставить вместо работающего движка.

**Пробелы:**
- нет общего `Brief → Choose Playbook → Plan/Cost Preview`;
- нет source-linked публичного аудита **конкретного предприятия**
  как prospect candidate и черновика адресного предложения;
- недостаточен охват интервью/JTBD/контекста реальных отзывов;
- нет отдельной методики «не задан вопрос, но есть смежная
  возможность для этого оборудования/материалов»;
- нет реальной системы набора и оценки false positive,
  перепроверки источников/возражений и качества рекомендаций;
- отсутствует перенос версий методик в каждую рекомендацию;
- мониторинг сигналов задач != market trends.

### Выводы первого аудита

1. Для **первого сервиса владельцам SMB** лучше сочетание
   **Prospecting (local SMB/demand signal) → Competitor Profiling
   quick scan → YAAI Wordstat/SERP → source-linked operator offer**.
2. Customer Research/JTBD полезен при наличии независимых отзывов
   и интервью; его confidence thresholds и потребность в выборке
   нуждаются в отдельном тесте.
3. SE Ranking/OpenSEO содержат **хорошие идеи организации workflow**,
   но не являются готовыми локальными источниками данных YAAI.
4. A/B Testing сохраняем для будущего экспериментального модуля.
5. Все выводы о качестве методик пока **качественные и предварительные**:
   содержимое инструкций изучено, ни один внешний playbook не
   был проверен на реальном исследовании внутри YAAI.

## D. Рекомендуемый первый end-to-end playbook для P0-B → P0-C

**Кодовое имя:** `operator-local-smb-diagnostic-v0` (пока **не рабочий Skill**).

Цель оператора: «Найди небольшие компании выбранной ниши/географии,
проверь по публичным данным, кому могла бы быть полезна упаковка
и оптимизация, и предложи один проверяемый пилот».

**Вход:** область, категория услуг/товаров, целевой размер бизнеса,
разрешённые площадки и бюджет/0 external paid calls.

**Шаги v0 (офлайн/сохранённые данные):**
1. Выбрать максимум **3–5** заранее подтверждённых организаций
   из разрешённых публичных источников.
2. Зафиксировать URL сайта, дату проверки, наблюдаемые разделы,
   наличие контактов/предложения и **открытые** факты без
   предположений о выручке/проблемах руководителя.
3. Сопоставить с 2–3 публично наблюдаемыми конкурирующими сайтами
   или SERP с одинаковым региональным/временным контекстом.
4. Добавить имеющиеся Wordstat-результаты, если регион и запросы
   сопоставимы, иначе записать «данных нет».
5. По каждому кандидату отделить OBSERVED, INFERRED, UNKNOWN,
   ALTERNATIVE EXPLANATIONS, REVIEW_NEEDED.
6. Создать **одну** операционную гипотезу для бизнеса: что
   можно проверить/исправить, зачем и какой минимальный
   эксперимент ответит на вопрос.
7. Сформировать отдельный короткий черновик адресного
   предложения без отправки сообщения.
8. Сохранить source snapshot, playbook version, evidence IDs,
   ограничение доступности данных и список незаполненных полей.

**Негативные примеры для теста:**
- нет сайта в одной выдаче, но сайт существует в другом источнике;
- красивые рейтинги или плохие отзывы при неясной достоверности;
- компания закрылась; дата и источник конфликтуют;
- один конкурент — маркетплейс, не реальный локальный конкурент;
- хороший сайт, но отсутствие метрик конверсий, поэтому нет
  доказанного «слива лидов»;
- Wordstat по другому региону/периоду не сравним;
- «нужен сайт» — не универсальный вывод: иногда важнее
  карточка организации, мессенджер или офлайн-контакт.

### Критерии готовности, чтобы честно закрыть P0-B

- Составить версионированный `PlaybookManifest`: кому подходит,
  source policy, входы/выходы, схему ссылок и статусных флагов,
  необходимые инструменты, ограничения затрат/времени, разрешения.
- Подготовить **10–20 проверенных вручную** сценариев, включая
  отрицательные и неоднозначные, и набор expected decisions;
  выборка — цель подготовки, **не** доказанный универсальный минимум.
- На одних и тех же данных сравнить текущие YAAI Skills vs
  новый playbook по traceability, ложным предложениям,
  полезности одной рекомендации, стоимости, времени и пропускам.
- Проверить licensed data и запрет unsafe tool execution;
  изучить зависимости/права выбранного адаптера, не
  исполнять неизвестные внешние scripts.
- Выбрать **один** первый внедряемый сценарий и подтвердить,
  что не ломаются CLI/MCP/Studio или Evidence Report v1.

После этих критериев P0-B можно пометить готовым. До этого
документ — **аудит-основание**, а не внедрённый маркетинговый Skill.

## E. Что принципиально не делаем

Не копируем чужие Skills в YAAI только за известность; не
переносим универсальные рейтинги аккаунтов или гарантию
результата; не делаем автоматические массовые письма; не
подключаем чужие платные MCP без согласования; не путаем
предварительную диагностику **публичной страницы** с
аудитом внутренних продаж, прибыли или финансов клиента.
