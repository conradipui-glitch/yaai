# YAAI Product Blueprint v2 — простой вход, исследование, знания, действия, рост

Статус: **согласованное направление продукта и новая последовательность планирования**, 2026-10-28.
Это **проектная спецификация, а не заявление о реализованных функциях**.
Действующий поэтапный контракт безопасности: [yaai-delivery-plan.md](yaai-delivery-plan.md).
Предыдущий исторический эскиз: [yaai-studio-roadmap.md](yaai-studio-roadmap.md).

## 1. Продуктовое обещание

**YAAI — виртуальный маркетинговый отдел** с простым русскоязычным входом.
Пользователь описывает бизнес и результат естественным языком; YAAI составляет
план, показывает охват и ожидаемые расходы, после разрешения собирает
источники, сохраняет проверяемые знания, предлагает решения и отдельно
помогает создавать/публиковать/измерять материалы.

Не превращать UI в каталог CLI-команд. CLI, локальный/удалённый MCP,
Telegram и встроенный Web Studio — **разные клиенты одного движка**, а не
четыре копии бизнес-логики. Внешний Harness с Agent Skills может работать
без UI и без обязательного универсального платного LLM API. Jev — ограниченный
движок решений, не универсальный собеседник и не гарант истины.

Главная граница: **простота для человека ≠ неявное разрешение на платные
вызовы, публикацию или изменение рекламы**.

## 2. Путь пользователя — минимум сложности снаружи

Начальный экран показывает один основной ввод:

> «Чем занимаетесь и что хотите получить? Например: ремонт стиральных
> машин в Омске. Хочу понять рынок и наполнить сайт».

После сообщения система в разговорном виде уточняет только *критически*
недостающее (география, B2C/B2B, сайт, если от него зависит результат).
Вместо огромной анкеты предлагает понятные варианты:

- **Разобраться в рынке** — спрос, запросы, источники, конкуренты, проблемы.
- **Понять покупателей** — сегменты, мотивации, вопросы, персоны-гипотезы.
- **Подготовить сайт** — структура страниц, темы и черновики.
- **Полный маркетинговый пакет** — общая исследовательская база с выводами
  и приоритетами, затем подготовка материалов без повторного сбора данных.

Пользователь может выбрать один модуль или всё вместе. «Полный пакет»
запускает только **релевантные** источники и способы анализа, а не все API
подряд. Перед исполнением виден человеческий план, перечень платных шагов,
диапазон бюджета или «стоимость неизвестна», оценка готовности источников
и границы результата. Можно удалить/отложить шаги. Без подтверждения
внешних затрат и чувствительных действий — только план или безопасная
офлайн-работа.

Результат представлен рабочими карточками и обычным текстом:
«Нашли», «Что это значит», «Что можно сделать», «Проверить источник»,
«Подготовить материалы», «Следующий замер». Инструменты и их параметры
раскрываются по желанию, а не обязательны для пользователя.

**Навигация:** Проекты → внутри проекта Чаты, Исследования,
База знаний, Материалы, Эксперименты/Результаты. Иконка/цвет проекта,
поиск, версии, возвращение к обсуждению. Чат — **представление
контекста/поручений**, не единственное место хранения истины.
UI первой версии не обязан показывать все будущие разделы: раскрывать
их по мере готовности и необходимости.

### Обучение в духе «открывающихся механик»

Три уровня:
1. Контекстная подсказка в 1–2 предложения рядом с действием.
2. Небольшая интерактивная демонстрация «для чего это» и «что изменится».
3. Необязательная миссия-урок: пример → проба на демонстрационных данных
   → объяснение расчёта → проверка понимания → применить к проекту.

Например, A/B: две версии заголовка → случайное разделение людей →
целевая метрика → интервал и ограничения. Учебная симуляция **не равна**
запущенному эксперименту и всегда явно отделена от реальных метрик.
Существующий Knowledge Layer CTR/CVR — исходный вертикальный модуль;
не строить заранее гигантский обучающий фреймворк.

## 3. Классификация задачи и выбор исследования

Маршрутизатор строит **профиль ниши (niche brief)**:
сфера/подкатегория, география, B2C/B2B, товар/услуга/цифровой продукт,
покупательская задача, экономические сегменты, сезонность,
длина цикла сделки, локальный/удалённый спрос, регулируемость/риски,
имеющийся сайт, рекламные/аналитические подключения и неизвестные поля.

Профиль определяется частично из сообщения, частично из источников,
а спорные/незаполненные поля **не выдумываются**. Он определяет
**план исследования**, а не заранее правильный ответ.

Например, локальный ремонт бытовой техники:
проверяем коммерческие запросы Wordstat, локальную SERP-выдачу,
сайты конкурентов, открытые отзывы и обсуждения, цены/условия с датами,
первичные возражения и существующий сайт. Для B2B SaaS порядок
и допустимые источники будут другими. Для необязательных источников
показывать «нет подключения / невозможно проверить / отложено».
Законность, правила площадки, доступность API, приватность и бюджет —
часть source policy, а не задача случайного LLM-промпта.

## 4. Внутренние слои — стабильные границы, не большой рефакторинг сразу

\`\`\`text
Одна строка запроса / чат / внешний MCP / Telegram
        ↓
Brief: ниша + цель + доступные контексты + ограничения
        ↓
Planner: пакеты задач и версии проверенных playbooks / Agent Skills
        ↓
Preview: план, доступные источники, бюджет, разрешения
        ↓
Executor: ограниченные возобновляемые jobs → адаптеры источников
        ↓
Evidence Store: снимки + наблюдения + контекст + проверки
        ↓
Knowledge Base: гипотезы + выводы + сегменты + связи/версии
        ↓
Report / Persona / SEO Brief / Content Draft / Site Export
        ↓ (только после отдельных разрешений)
Publish / Analytics Snapshot / A/B Evaluation / Recommend Revision
\`\`\`

Все клиенты используют **одну систему задач, разрешений, учёта стоимости
и provenance**. Пользователь не должен знать имена уровней.

**Режимы действий:** read, draft, collect (сеть/возможная стоимость),
publish (внешние изменения), ads-write (реклама), administer (доступы).
Разрешения привязаны к проекту, конкретному действию, лимиту,
провайдеру и сроку; отказ и отмена не требуют пересоздания проекта.
Dry-run по умолчанию. Никаких универсальных разрешений «делай всё»,
автоматической оплаты или открытого shell с правами сервера.

## 5. Общая база знаний — фундамент до «полного пакета»

Нынешние workspace/case, snapshots, tasks, evidence reports и Skills
сохраняются. **Новый уровень должен их объединять, а не заменять**.

Планируемые сущности (контракты утвердить на узком вертикальном срезе):

| Объект | Что хранит |
| --- | --- |
| Project | Бизнес, география, доступы/разрешения по ссылкам, настройки, значок/цвет |
| Conversation/Brief | Контекст чата, цель, ограничения, версия исходного задания |
| Plan/Run/Task | Версия методики, шаги, разрешения, статус, попытки, стоимость, ошибки |
| Source/SourceSnapshot | URL/платформа/идентификатор, время наблюдения, допустимый снимок/хэш, свежесть, доступ |
| Observation | Текст или метрика, исходный контекст, дата, связь с SourceSnapshot, тип сигнала |
| Claim/Review | Вывод и **ссылки на наблюдения**; статус гипотезы/проверки/возражения/устаревания |
| AudienceSegment/Persona | Сегмент, потребность, бюджет/мотивации с доказательствами и явно помеченными предположениями |
| ResearchArtifact | Версионированный отчёт, график, страница, карта, SEO-бриф и исходные идентификаторы |
| ContentVersion/Deployment | Черновик/проверенная версия/размещение, diff, дата, цель, источник знаний, возврат |
| MetricSnapshot/Experiment | Определение метрики, окно атрибуции, источник, A/B-разбиение или обычное сравнение, неопределённость |

Идентификаторы стабильны; кросс-проектные ссылки запрещены по умолчанию.
Запись новых источников/версий append-only там, где нужна история.
Отдельно проверять хэш неизменяемых артефактов, вводить миграции версии
схем, чтобы старые данные продолжали читаться. Черновики можно менять,
исходную историю — не подменять.

**Отчёт — материализованное представление базы**, а не сама база.
Evidence Report v1 создан в PR #42 (2026-10-08 UTC; 09.10 по Омску)
специально для Pain Discovery; \`yaai-evidence-report\` v1 содержит
\`observations\`, \`claims\`, \`provenance\`, \`summary\`, \`quality\`.
Он **наш собственный контракт**, не обязательный сторонний формат.
Для сырого списка отзывов нужен валидированный адаптер в слой
Observation/SourceSnapshot, затем версия отчёта; **не пытаться
насильно упаковать все будущие типы данных внутрь v1**.
v1 должен оставаться читаемым при появлении новых схем/проекций.

### Повторное использование дорогих данных

«Один заход» означает **один сбор свидетельств с максимальным разумным
переиспользованием**, а не однократный навсегда полный анализ.
Отдельные статьи, персоны, SEO/Geo-брифы и рекомендации ссылаются
на версии сохранённых знаний. Если источник стар, противоречив или
изменился — запрашивать **точечное** обновление, не заново собирать всё.
Хранить \`observedAt\`, \`fetchedAt\`, источник/право на хранение,
неизвестные поля и причину устаревания.

## 6. Source integrity: жалобы, контраргументы, подозрительные отзывы

Любое утверждение из открытого источника сохраняется прежде всего
как **заявление автора**, а не установленный факт. По возможности
сохраняются source URL, platform, item ID, дата публикации, дата
сбора, фрагмент и контекст ветки, родитель/ответ/возражение,
отредактировано/удалено/недоступно, метод сбора и разрешённый
объём цитирования. Для необозримых/закрытых источников не заявлять,
что они прочитаны. Авторов и персональные данные минимизировать.

Гипотеза о недостоверности отзывов — **review flag**, не публичное
обвинение и не бинарный вердикт «фейк». Поводы посмотреть подробнее:
плотная временная серия, повторы формулировок, конфликтные даты,
аналогичные тексты, необычная структура аккаунтов (только
наблюдаемое/допустимое), массовая смена оценок. Нужны контроль
по обычному поведению площадки и независимые признаки;
сходство текста само по себе не доказывает накрутку.

Проверка источника при первом чтении и при повторном обращении:
- исходная запись и доступность; не считать 404 доказательством фейка;
- ответы автора/компании/третьих лиц, исправления и контекст ветки;
- независимые подтверждения и возражения, временные кластеры;
- изменение статуса: observed → contested → supported/rejected/unknown/
  stale (статусы утвердить в схеме позже);
- дата последней проверки и рекомендуемый интервал перепроверки
  по типу источника, а не бесконечный polling.

Отделять поисковые **запросы** (информационная потребность, Wordstat),
SERP **сниппеты** (отрывок выдачи, не прочитанная страница),
публичные **отзывы** (утверждения автора), аналитические
**измерения**, AI **гипотезы** и вручную **проверенные факты**.
Не выдавать Jev probability за правдоподобие утверждения.
Все выводы должны позволять открыть исходное наблюдение и увидеть,
почему YAAI к нему пришёл.

## 7. Персоны и сегменты — четыре уровня доказательности

Сегментацию выбирать по задаче: бюджетная / средняя / премиальная
(или иные явно применимые группы); B2B-клиенты, роли в покупке,
задачи, триггеры, барьеры, каналы и критерии выбора.
Не навязывать три ценовых сегмента, если реальных оснований нет.

Выход: **несколько карточек персонажей** с задачей, потребностями,
условной ситуацией, ценовым диапазоном (если наблюдён), типичными
вопросами, барьерами и подходящим предложением.
Профессия, внешность, дневной распорядок и биография — **выдуманный
иллюстративный сценарий**, если они не подтверждены исследованием;
нельзя выдавать их за найденную статистику аудитории.
Изображения аватаров допустимы только как условные иллюстрации,
не «реальные представители сегмента».
У каждого поля: наблюдение / аналитический вывод / гипотеза /
пример для объяснения / неизвестно и связи с источниками.
Уверенность, количество наблюдений и пробелы явно доступны.

Результат полного research pack: рынок и ниша; фактические
поисковые сигналы; конкуренты с условиями и датами; Pain Map;
сегменты/персоны; контент- и SEO/GEO-возможности; пробелы и
рекомендуемые эксперименты; источники и ограничения. Не заполненные
разделы отмечать «недостаточно данных», а не искусственно дополнять.

## 8. Playbooks / Skills — исследовать практики до автоматизации

Существующие Skills (\`pain-discovery\`, \`competitor-evidence\`,
\`seo-report\`, \`page-plan\` и другие) — исходное ядро, не
переписывать его вслепую. Добавить **аудит методик** как отдельный
этап планирования перед созданием универсального маршрутизатора.

Проверять:
1. Официальные рекомендации поисковых систем/платформ и документацию API.
2. Открытые репозитории marketing/SEO/research/agent Skills: читать
   **полный SKILL.md, references, scripts, licenses, commit history**.
3. Профессиональные форумы/кейсы: конкретная ниша, страна, дата,
   контекст и наличие измеримого результата. Голоса форума и
   популярность репозитория ≠ доказанная эффективность.
4. Сравнительные тесты на размеченных примерах: корректность,
   воспроизводимость, стоимость, сроки, ложные сигналы,
   отсутствие вредных действий.

Результат: реестр \`PlaybookManifest\` со специализацией,
схемой входов/выходов, источниками и версиями, ограничениями,
обязательными review gates, поддерживаемыми инструментами,
провайдерскими расходами и экспериментальной оценкой качества.
Библиотека обновляется версиями; существующие результаты хранят
ID/версию использованной методики. Навыки подключать по требованию
(progressive disclosure) и только после просмотра кода/лицензии/
безопасности. Никаких чужих SKILL.md «копировать и вставить»
без прав, ни чужих исполняемых скриптов из интернета по умолчанию.

Начальная очередь аудита: исследование спроса, анализ SERP/конкурентов,
сбор и проверка отзывов, JTBD/персоны/сегменты, контент-планирование,
people-first SEO/GEO, измерение и A/B. Первые playbooks должны
проверяться на одном безопасном локальном сценарии.
Официальная основа для контентной политики:
https://developers.google.com/search/docs/fundamentals/creating-helpful-content
Документация переносимых Skills:
https://learn.microsoft.com/en-us/agent-framework/agents/skills

## 9. После исследования — материалы, публикация, измерение

**Ступень A — знание → материалы:** контентные кластеры, структура
страниц, SEO/GEO-брифы, несколько редакторских вариантов, статьи
и посадочные. Содержимое основано на версиях наблюдений и принципах
people-first, а не «массовом рерайте ради ранжирования».
Проверка фактов, источников, права на контент и стиль — до публикации.

**Ступень B — публикация:** коннектор Git/PR предпочтителен для
версионных сайтов; SSH/SFTP/CMS только в изолированной области
разрешённых действий. Хранить базовую версию, diff, исходные файлы,
резервную копию, результат dry-run и план отката. Для production
требуется отдельное явное подтверждение конкретного изменения.
Доступы не сохранять в чатах/отчётах/HTML/репозитории.

**Ступень C — измерение:** по явному подключению Метрики,
Webmaster, рекламных платформ или другой аналитики собирать
согласованные снимки с временем, часовым поясом, URL, версией
опубликованного материала, определением метрики и окнами атрибуции.
Частота — адаптивная: часовые/дневные данные только когда объём
и API позволяют; для редкого трафика лучше недели.
Не выдавать «после публикации стало лучше» за причинный эффект
без корректной экспериментальной схемы.

**Ступень D — A/B:** отдельный образовательный UI объясняет:
гипотеза → контроль/вариант → случайное закреплённое
распределение пользователей/сессий → основная метрика и guardrails
→ длительность/мощность/минимальный эффект → анализ →
проверка технической реализации → решение.
Если рандомизации нет — это **наблюдение до/после** или
SEO-эксперимент иной природы, не заявлять достоверный A/B.
Для поискового SEO двух похожих URL могут возникать каннибализация
и проблемы индексации; не публиковать дубли автоматически.
Учёт сезонности, малых выборок, множественных сравнений и
задержанных конверсий обязателен.

## 10. Новый порядок реализации — чтобы не переписывать всё снова

| Шаг | Что делаем | Проверяемый результат | Граница |
| --- | --- | --- | --- |
| **P0-A** | Зафиксировать UX/Brief/объекты проекта, контракты и границы (этот документ) | Один согласованный сценарий и схема связей | Только docs/design, нет нового backend |
| **P0-B** | Аудит существующих Skills и 3–5 внешних методик; выбрать один исследовательский сценарий | Версионированный playbook с тест-кейсами | Не выполнять непроверенный чужой код |
| **P0-C** | Минимальный \`SourceSnapshot → Observation → Claim\` adapter для реального набора и проектное хранение; сохранить Evidence Report v1 совместимым | Повторное чтение одного набора без платного сбора, корректные ссылки, контраргументы и статусы | Нет универсальной БД и live scraping сразу |
| **P0-D** | Тонкий \`Brief → Plan → Preview → Approved Run\` поверх уже существующих CLI/Tasks/Skills | Пользователь ставит одну цель, YAAI запускает **один** ограниченный end-to-end сценарий и переиспользует данные | Новые платные вызовы только после явного разрешения |
| **P0-E** | Простая первая страница Studio, проект/чаты и исследовательские пакеты; общий контракт для MCP/Harness | Один и тот же результат доступен в Studio и внешнему агенту, без дублирования движка | Чат и агент добавлять вертикально, не как новый монолит |
| **P0-F** | Исследовательский пакет и 2–3 помеченные гипотетические персоны из сохранённых знаний | Отчёт + сегменты + источники + недостающие поля, без выдуманных фактов | Без автоматической публикации |
| **P1-A** | Черновики статей, SEO/GEO-брифы, версии и правки | Проверяемые материалы из сохранённого research pack | Publish требует отдельного подтверждения |
| **P1-B** | Безопасное подключение сайта, Git/PR, ограниченный деплой/откат | Проверенный ручной publish и rollback | Никаких универсальных root-ключей |
| **P1-C** | Аналитика/мониторинг с версионированием изменений и уроком метрик | Повторяемые сравнения по сохранённым снимкам | Изменения после даты ≠ причинность |
| **P2** | Корректные A/B, VPS-исполнитель, уведомления/Telegram, расширение Skills и обучения | Пилот с разрешениями, реальным измерением и восстановлением | Усложнять по подтверждённой пользе |

Это **зависимости**, а не обещание календарных сроков или строго
линейная очередь для каждого UI-компонента. Небольшой прототип
строки ввода допустим раньше P0-E, но не превращать его в ещё
один неработающий mock. Исследование навыков P0-B и простое UX
можно вести параллельно, если они не меняют data contracts.

### Definition of first truly useful YAAI release

Начинающий пользователь без знаний Wordstat/MCP:
создаёт проект → пишет «ремонт стиральных машин в Омске,
хочу рынок и материалы сайта» → видит и редактирует план
(исследование/персоны/сайт/полный пакет) и стоимость →
с разрешениями получает **одну** реально выполненную локальную
исследовательскую цепочку → изучает источник/сомнение в выводе →
получает долговечный исследовательский пакет и отдельные
черновики материалов → повторно открывает проект, не платя
за тот же набор данных → внешний агент через тот же engine
может прочитать результаты и согласовать следующий шаг.
Публикация и A/B — **следующие** самостоятельные версии,
не условие первого MVP.

### Проверки до каждого слияния

- Синтетические + разрешённые реальные тестовые данные; raw-source
  можно пересмотреть; есть ли ответ/возражение/смена статуса;
- неверный проект, дубли, удалённые источники, испорченный JSON,
  источник с ненадёжным контекстом, устаревание, retry/прерывание;
- сохранение старых Evidence Report v1 и старого CLI/MCP поведения;
- dry-run по умолчанию, 0 внешних платежей и 0 production writes в тестах;
- доступность/понятность русского UI для непрофессионала;
- тест UI в браузере отдельно от CI/API; не выдавать один за другое.

## 11. Что уже реализовано и что ещё только в плане

**Есть в main (с разными ограничениями):** Wordstat/SERP/Webmaster,
Pain Discovery, Jev, Page Planner, Evidence Report v1, source review/quality
частично, локальный task registry/offline runner, readonly MCP, Agent Skills,
Studio Light RU с чтением проектов и сохранённого Pain Report,
первый Knowledge Layer и локальный inbox сигналов.

**Нет / не проверено production:** единый UX «одна строка → полный пакет»,
универсальный реестр источников и контекстно-проверяемых отзывов,
project chat/agent execution, general model router, полноценная база
сегментов/персон/контента, безопасная публикация, Метрика/онлайн A/B,
постоянный VPS worker и Telegram-бот. Нынешний отдельный
VPS read-only шаблон не равен публичному развёртыванию.

**Не удалять и не перезаписывать** существующие артефакты ради нового
плана. Реализация идёт маленькими PR с обратной совместимостью и
отдельными честными статусами функций.
