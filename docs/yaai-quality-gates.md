# YAAI — обязательные проверки и согласованность инструментов

**Статус:** единый протокол приёмки каждой итерации и каждого этапа (2026-10-28).
Используется вместе с [журналом итераций](yaai-iteration-tracker.md),
[планом разработки](yaai-delivery-plan.md) и
[Product Blueprint v2](yaai-product-blueprint-v2.md).

## Главное правило: нет подтверждённой проверки — нет перехода

**Разработать ≠ внедрить ≠ проверить ≠ принять.**
Этап/итерация закрывается **только** при выполнении применимых
критериев проверки и записи доказательств. Успешный GitHub CI —
не синоним полного испытания работающего продукта. Если необходим
ручной или сквозной тест и он не проведён — статус
`ОЖИДАЕТ ПРОВЕРКИ`, а не `ГОТОВО`.

Возможные статусы: `ЗАПЛАНИРОВАНО`, `В РАБОТЕ`,
`РЕАЛИЗОВАНО — НЕ ПРОВЕРЕНО`, `ПРОВЕРКА НЕ ПРОШЛА`,
`ОЖИДАЕТ ПРОВЕРКИ`, `ПРИНЯТО`, `ЗАБЛОКИРОВАНО`.
Для документального аудита `ПРИНЯТО КАК ДОКУМЕНТ` не означает
`ПРОВЕРЕНА ЭФФЕКТИВНОСТЬ` — это отдельный критерий P0-B.5.

Не меняем основной P0-A…F / P1 / P2 план. Quality gate —
**не новый этап**, а обязательное условие закрытия **каждой**
подзадачи и перехода между этапами. Для каждого пункта тестов
фиксируется `PASS / FAIL / NOT RUN / NOT APPLICABLE`;
`NOT APPLICABLE` требует объяснения. `NOT RUN` не равен PASS.
Обнаруженное несоответствие — исправление в текущей итерации
и повторный прогон затронутых проверок плюс регрессия.

## 1. Уровни проверки

| Уровень | Что проверяем | Примеры | Когда обязателен |
| --- | --- | --- | --- |
| **T0: соответствие заданию** | Чётко совпали входы/выходы, сценарий, версии и границы с утверждённым plan/manifest | «Обещали один вывод — получаем связанный с источником вывод» | Всегда, включая docs |
| **T1: локальная корректность** | Unit, schema, business rules, ошибки, неизвестные значения, контрольные и отрицательные примеры | Поля `null` не равны нулю; неподдерживаемая категория отвергается | Для нового/изменённого кода и вычислений |
| **T2: контракт и обратная совместимость** | Вход/выход прежних команд, форматы, API/MCP, права доступа и миграции | Старый Evidence Report v1 читается, task registry не ломается | Когда меняется интерфейс/данные/интеграции |
| **T3: cross-tool / сквозной сценарий** | Один результат проходит путь через **два и более** связанных инструмента без искажения смысла | Wordstat→Pain→Report→Studio; registry→MCP→Studio | Всегда при появлении/изменении связи инструментов |
| **T4: воспроизводимость и консистентность** | Один набор с одинаковыми версиями приводит к тем же фактам; refresh, повторный запуск, кэш, прерывание и восстановление | Нет исчезнувших source IDs, случайных повторных затрат и потери истории | При сохранении/обновлении/планировщике/расходах |
| **T5: безопасность и бюджет** | Workspace isolation, secret masking, permission gates, лимиты, input injection, side effects | Чужой проект нельзя прочитать, dry-run ничего не публикует/не покупает | Для любой работы с файловой системой, сетью, моделью, агентом, API или внешними действиями |
| **T6: живой пользовательский путь** | Реальный браузер/CLI/MCP, русские тексты и понятные состояния, наблюдаемость результата | «Новичок вводит нишу — видит план, источник и ограничение» | Для пользовательских интерфейсов и end-to-end релизов |
| **T7: качество решения** | Проверка полезности и ложных рекомендаций на вручную разобранной выборке; контроль слепых зон | «Слабый сайт» не превращается автоматически в «бизнес теряет продажи» | Для Skills, playbooks, классификаторов, рекомендаций и скоринга |

Тест «не применим» — не лазейка. Для итерации с документацией
T0 + проверка ссылок/формата/версионирования/соответствия плану
нужны всегда, а эффективность методики проверяется на её
запланированном **P0-B.4–5** benchmark. Для одного обновлённого
CLI тест браузера может быть N/A с объяснением; если CLI
используется Studio/MCP, их контрактные проверки всё равно нужны.

## 2. Инварианты — что не имеет права противоречить само себе

1. **Идентичность и изоляция:** общий project/case ID, стабильные
   source/observation/claim/task/artifact IDs. Никакой чужой проект
   не попадает в ответы, экспорт, кеши или поиск.
2. **Provenance:** каждый значимый вывод ссылается на сохранённое
   наблюдение, исходный URL/тип источника, дату и версию методики;
   у отсутствующего URL не появляется вымышленная ссылка.
3. **Семантическая честность:** Wordstat-фраза = поисковая фраза,
   SERP snippet = фрагмент выдачи, отзыв = заявление автора,
   Jev verdict = оценка модели, inference = гипотеза.
   Они не становятся «подтверждённой жалобой» по дороге в UI.
4. **Счётчики и единицы:** сумма категорий допустима только при
   непересекающихся множествах; уникальные URL ≠ количество
   отзывов; частотность запроса ≠ число покупателей/переходов.
   У каждой метрики есть единица, регион, период и метод расчёта.
5. **Время и сравнимость:** `observedAt` ≠ `fetchedAt` ≠
   `processedAt`; используем регион, часовой пояс, окно сбора,
   версии источников и статусы устаревания. Разные периоды и
   регионы не сравниваем как однородные без поправки.
6. **Отсутствие данных:** `unknown / missing / unavailable /
   contested / stale` не заменяются 0, false, высокой оценкой
   уверенности или красивыми фиктивными KPI.
7. **Версии и обновления:** новая проверка может обновить текущую
   рекомендацию, но не уничтожает старый снимок и первичный
   контекст. Сохраняется связь «что знали, когда решили, что
   опубликовали, что измерили позже».
8. **Стоимость и права:** любое collect/paid/publish/ads-write
   действие имеет отдельный явно разрешённый scope, предварительный
   budget/unknown-price, audit trail и stop-on-limit.
   Отображение отчёта/перезапуск не запускают платные действия.
9. **Контракты клиентов:** CLI, MCP и Studio обращаются к одному
   сохранённому результату/бизнес-логике, а не считают по-разному
   одно и то же в трёх местах.
10. **Выводы и решения:** полезность рекомендации связана с
    источниками, возможностями бизнеса и альтернативными
    объяснениями. Допускается честный итог «данных недостаточно»,
    а не обязательная рекомендация.

## 3. Матрица сквозных проверок (переиспользуемая)

| Путь между инструментами | Позитивная проверка | Негативная и регрессия | Состояние |
| --- | --- | --- | --- |
| **Wordstat → snapshot → Pain classification** | Сохраняется фраза, период, регион, единица и provenance | Пересекающиеся фразы нельзя суммировать; отсутствие volume ≠ 0; другой регион несовместим | Проверять при изменении связи |
| **SERP → snippet → Pain → Evidence Report** | ID, URL, дата, исходный тип и status остаются прежними | Сниппет не становится проверенным отзывом; плохие URL/дубли/контекст отклонены | Проверять при изменении связи |
| **Pain / Jev → Evidence Report v1 → Studio** | Совпадают число наблюдений, категорий, source IDs, review flags и значения | Неизвестная категория/несовпадающий счётчик → ошибка без подмены | Проверять при изменении связи |
| **Task registry → offline executor → MCP → Studio** | Одна и та же задача и статус видны во всех интерфейсах, а не клоны | Чужой case, повторённый запуск, interruption; нет неожиданного оплачиваемого run | Проверять при изменении связи |
| **SourceSnapshot → Claim → recommendation** *(будущий P0-C/F)* | Источник открывается, смысл и дата сохранились, вывод воспроизводим | Возражение/исправление/недоступность → review, а не ложное подтверждение | Запланировано |
| **Prospect → Audit → Offer** *(будущий P0-C/F)* | Оффер объясним наблюдением и конкретным ограничением бизнеса | Нет сайта в 1 SERP ≠ нет сайта; нет аналитики ≠ упущенная выручка | Запланировано |
| **Plan → Approval → Executor → Artifacts** *(будущий P0-D)* | Без подтверждения только план/dry-run; после — в рамках scope и бюджета | Ошибки, ретраи, отключённый API, лимит; никаких повторных скрытых затрат | Запланировано |
| **Content Version → Publish → Metric Snapshot → Insight** *(будущий P1)* | Версия и время публикации связаны с измерениями и откатом | Разница до/после ≠ причинность; нет трафика ≠ «0 спроса»; нет сайта без разрешения | Запланировано |

**Статус в таблице — требование к будущим проверкам, НЕ утверждение,
что перечисленные end-to-end тесты уже прошли.**
Матричные тесты со временем превращаются в реальные `selftest`
или фикстуры с ожидаемым выводом. При каждом PR автор явно
называет затронутые пути, а не обещает проверку всех комбинаций.

## 4. Наборы данных и обновления

- **Фикстуры**: небольшие детерминированные синтетические и
  разрешённые архивные реальные примеры. Для каждого — вход,
  expected output, лицензия/разрешение, дата и версия.
- **Golden decisions**: отдельно от вывода модели хранить
  обоснованный человеком эталон «считать / не считать /
  недостаточно данных»; модель может ошибаться и должна
  сравниваться с эталоном, а не сама с собой.
- **Контрактные версии**: фиксируем версии схем/Skills/моделей;
  изменение версии требует сравнительного/миграционного теста.
- **Переиспользование**: повторное чтение одной версии
  возвращает те же исходные значения и не обращается к платным
  источникам; новый сбор создаёт новый snapshot.
- **Перепроверка источника**: найдено дополнение, опровержение
  или недоступность — хранить новый verification event; прежний
  факт наблюдения не стирается, статус вывода может измениться.
- **Числа/формулы**: контроль сумм на раздельных категориях,
  округления, `null`, временных окон и того, какие значения
  были оценены, а какие реально измерены.
- **Свойство idempotency**: повторная обработка того же
  snapshot не создаёт дублирующиеся сущности/платежи или
  расходящиеся решения без задокументированной причины.
- **Zero-API dry-run**: все CI и unit/contract/fixture tests
  по умолчанию без реальных платных API и внешних записей.
  Необязательные live smoke для внешних провайдеров — отдельно,
  с явным разрешением и бюджетом.

## 5. Acceptance Card — заполнять для каждой итерации

| Поле | Что записать |
| --- | --- |
| Iteration ID | `P0-B.3` / `P0-C.1` / … |
| Цель и исходные ограничения | Одна проверяемая задача + что НЕ делаем |
| Изменённые контракты | Какие входы, форматы, версии, права |
| Артефакт | PR/commit, Skill/manifest, code, schema, report |
| Проверки T0–T7 | Для каждого: PASS / FAIL / NOT RUN / N/A + причина |
| Cross-tool пути | Конкретные связки из матрицы и результаты |
| Фикстуры и negative cases | Какие использовались, даты/ожидаемые решения |
| Фактический прогон | Команда, CI run URL, браузер / CLI / MCP / manual steps |
| Согласованность/расхождения | Что не совпало, какой источник истины, как исправили |
| Повторная проверка | Что перезапущено после исправления |
| Решение | ACCEPT / BLOCK / REWORK, основание |
| Следующая итерация | Новый номер **только после ACCEPT** |

**Проверка с ошибкой:**
1. Записать воспроизводимый дефект с исходным набором/expected/actual.
2. Вернуться к изменённому компоненту, устранить причину, не маскируя
   несовпадение в другом интерфейсе.
3. Запустить нарушенный тест, соседние контракты и основной регрессионный набор.
4. Заполнить новую фактическую проверку; только после ACCEPT
   обновить статус в журнале и переходить дальше.

**Сложный случай:** если тест **впервые становится возможен только
после последующего этапа**, это можно обозначить как
`BLOCKED BY P0-X` с явным контрактным тестом на текущем этапе
и будущим интеграционным gate. Это НЕ позволяет объявлять
полностью работающий сквозной сценарий раньше времени.
Готовность текущей итерации означает только её честно ограниченную
сферу, а не готовность всего продукта.

## 6. Как применить уже на ближайшем P0-B.3

Итерация P0-B.3 — **методика, а не программа**:

- T0: Manifest описывает входы, источники и проверяемые выходы;
- T1/T7 в документальном режиме: пройти вручную **минимум три**
  характерных сценария (хорошие данные, спорные, отсутствие
  источника) и проверить, что вывод закономерен;
- T2: имена сущностей и контракты не ломают текущие
  `Pain / Evidence Report v1 / CLI/MCP`;
- T3: показать на фикстуре, как один source observation
  будет использован в prospect audit, затем в обоснованном
  черновике оффера; пока как проектный trace, **не живой pipeline**;
- T4: воспроизвести решение по тем же входам, если не меняются
  версия методики и факты;
- T5: в правилах запрещены автоматическая отправка сообщений,
  обход площадок, списания и чтение чужого проекта;
- T6: N/A для работающего UI; его ещё не внедряем.

P0-B.4 расширяет и проверяет golden fixtures, P0-B.5
сравнивает подходы на той же размеченной выборке.
**Только P0-B.5 с Acceptance Card = ACCEPT закрывает P0-B**.

## 7. Отчёт о выполнении каждой задачи в чате

Всегда коротко и одинаково:

**Этап:** P0-B · **Итерация:** P0-B.3 · **Результат:** …
**Проверка:** T0 ✓; T2 ✓; T3 проектная / не запущена; T6 N/A.
**Расхождения:** … · **Решение:** ACCEPT / REWORK / BLOCK.
**Следующее:** P0-B.4 (только если принято).

Не сообщать «полностью протестировано», если есть только
`npm run check` без пользовательского/сквозного испытания.
